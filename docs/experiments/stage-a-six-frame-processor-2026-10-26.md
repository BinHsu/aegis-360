Date: 2026-10-26. Host: Apple M4 MacBook Air, macOS 27.0.1, Xcode 27.2 RC (27B48). The pinned `mlx-swift-lm` 3.32.3 snapshot and the already verified Metal library were used. Source, cache, scratch, binaries and logs stayed under `/Volumes/T7/aegis-360-items/build/`; the graph, build and runs used outer `sandbox-exec` network denial.

The frozen Stage A request has six media items in projection row order. The pinned SmolVLM2 processor permits one image or one video in a call. Its video path accepts caller-supplied frames and applies `MediaProcessing.asProcessedSequence`; the latter samples times relative to zero and may select fewer frames if caller timestamps retain absolute source times. `StageAFrameSequence.make(images:)` therefore requires exactly six images, assigns ordinal timestamps `0…5`, and requests exactly six frames. This function carries no source timestamps, labels or camera instructions.

The v1 synthetic executable used six distinct 2×2 color frames directly. The pinned processor returned six frames, timestamps `0…5`, and strictly ordered distinct pixel sums. Reversing the pixels while keeping timestamps fixed produced the expected order failure. The v1 build and logs remain on T7; this checks processor behavior but does not exercise the reusable input function.

The v2 executable uses `StageAFrameSequence.make(images:)` and checks the same processor result. It also submits reversed pixels to test the order oracle and five images to test the exact-count rejection. The isolated graph contained only local paths.
